Visão geral

Dois projetos na Vercel: o site só exibe, a API calcula e é a única que fala com o banco e os serviços. Tudo chega à Vercel pelo GitHub, depois dos testes.

As setas indicam quem chama quem. Os serviços tracejados ainda são propostas.

Banco de dados

Um projeto novo na Neon, só Postgres relacional, sem JSONB. Um schema por módulo e um por sistema de RPG, com a edição no nome. A divisão dos módulos da plataforma espera a sua lista de funcionalidades.

Embaixo, o modelo envelope: cada informação mora numa tabela só, e o banco garante que o envelope e a ficha do sistema não divergem.

InformaçãoOnde moraPode divergir?
Nome, dono, favorita, lixeira, datasSó no envelopeNão. Existe uma vez só.
Atributos, classes, perícias, magiasSó na tabela do sistemaNão. Existe uma vez só.
id (UUIDv7)Nas duasNão. Na tabela do sistema é chave estrangeira do envelope.
Tipo do sistemaEnvelope e, como constante, a tabela do sistemaNão. A constante é fixada por CHECK, e a chave estrangeira composta (id, system) obriga os dois a serem iguais.

Código do backend

Python, organizado por módulo primeiro. Dentro de cada módulo, as camadas da clean architecture. O import-linter faz a CI falhar se alguma camada importar o que não pode.

Setas = "depende de". O domínio não depende de nada, e o service fala com o banco só por interfaces.

Entrega: do commit ao site

Confirmado: nada chega à Vercel sem passar pela CI, e cada PR tem um preview com banco e API próprios. Os passos abaixo são a proposta de pipeline.

Qualquer etapa que falhar interrompe a pipeline antes de publicar. Os previews usam dados fictícios, nunca os de produção.
